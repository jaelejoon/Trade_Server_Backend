# 백테스트 데이터 조회와 실행 API 설계

## 데이터 위치

화면과 향후 실행 엔진은 로그인 사용자에게 속한 PostgreSQL `candles_1m`의
`BTCUSDT` 행을 사용한다. 기존 수집·백테스트 코드가 같은 테이블을 사용한다.
CSV를 별도 경로로 읽으면 서버가 조회한 데이터와 시뮬레이션 입력이 달라질 수 있다.

- `id`는 기본 키다. `user_id`, `symbol`, `open_time` 조합에는 고유 제약이 있다.
- `open_time`에는 시간대 정보가 없는 UTC 시각을 저장한다. 가격과 거래량은
  `open`, `high`, `low`, `close`, `volume`에 저장한다.
- 확인하려는 계정으로 로그인하여 현황 API의 첫 봉·마지막 봉·고유 분봉 수를 조회한다.
  예상 분봉 수는 두 시작 시각의 차이를 분으로 나눈 값에 1을 더해 계산한다.
  점검 API는 그 범위 안에서 실제로 빠진 분봉 수를 반환한다.
- PR #1의 수집 스크립트는 `BTCUSDT_futures_1m.csv`를 만들고 적재용 SQL을 생성한다.
  그 SQL의 검증 기준은 3,793,090행과 첫·마지막 시작 시각
  2019-09-08 17:57 UTC, 2026-11-24 20:07 UTC다. 계정별 실제 DB 적재 상태는 확인 필요다.
- 첨부 `IdeaProjects.zip`은 백엔드·프런트 소스 압축본이다. 패키지 내부 테스트 데이터를
  제외하면 캔들 CSV를 확인하지 못했다. `BTC-백테스트-코드.txt`는 외부 CSV에서
  `timestamp,open,high,low,close,volume`을 읽는 코드다. 별도 대화에 언급된
  `V57_backtest_2026-11-25.zip`의 내용은 확인 필요다.

## 읽기 API

세 경로 모두 기존 로그인 인증을 사용한다. 현재 진행 중인 1분봉은 제외한다.
시각은 UTC 오프셋을 포함한다.

| 요청 | 응답 |
|---|---|
| `GET /backtests/data/status` | 종목, 원본 봉 간격, 첫·마지막 봉 시작 시각, 분 단위에 정렬된 고유 시작 시각 수, 누락 구간 수 |
| `GET /backtests/data/integrity` | 현황 필드와 누락 분봉 수, 중복 시각 수, 초과 중복 행 수, 분 단위에 맞지 않는 행 수 |
| `GET /backtests/data/candles` | 종목, 요청한 봉 간격, 오래된 순 OHLCV, 다음 요청의 커서 |

점검은 저장된 첫 봉과 마지막 봉 사이의 연속 누락을 구간 하나로 센다. 양 끝 바깥은 누락으로
세지 않는다. 데이터가 없으면 첫·마지막 시각은 `null`이고 개수는 0이다.

캔들 조회의 필수 파라미터는 오프셋을 포함한 `start`, `end`다. 범위는 `[start, end)`이며
봉 전체가 범위 안에 있어야 한다. `interval`은 `1m`, `15m`, `1h`, `4h`를
지원한다. 상위 봉은 UTC 경계를 기준으로 첫 시가, 최고가, 최저가, 마지막 종가, 거래량 합을
사용한다. 정렬된 분봉이 매 분에 한 건씩 존재해야 반환한다. `limit`은 기본 500,
최대 1,000이다. 다음 페이지는 같은 범위·간격에 `next_cursor`를 `cursor`로 전달한다.
커서가 `null`이면 마지막 페이지다. 조회 도중 과거 데이터가 적재되면 이미 지난 커서
이전 구간에는 반영되지 않으므로 범위 처음부터 다시 조회한다.

```json
{
  "symbol": "BTCUSDT",
  "interval": "1m",
  "start": "2025-01-01T00:00:00+00:00",
  "end": "2025-01-01T08:59:00+00:00",
  "candle_count": 538,
  "gap_count": 1
}
```

점검 응답은 이 필드에
`{"missing_minutes":2,"duplicate_timestamps":1,"duplicate_rows":1,"misaligned_rows":1}`을 추가한다.

```json
{
  "symbol": "BTCUSDT",
  "interval": "15m",
  "items": [
    {"open_time":"2025-01-01T00:00:00+00:00","open":1000,"high":1016,"low":998,"close":1015,"volume":30}
  ],
  "next_cursor": "2025-01-01T00:00:00+00:00"
}
```

예시는 테스트용 데이터다. PostgreSQL 16은 집계에 쓰는 `date_bin`을 지원한다.
현황과 점검은 사용자별 원본 범위를 집계하며 긴 기간의 캔들 조회도 DB에서 집계한다.
대량 데이터 사용자에 대한 운영 쿼리 실행 시간은 확인 필요다.

## 후속 단계 백테스트 실행 API 설계

기존 `POST /backtests/run`은 V57 엔진과 사용자 전략 설정을 사용한다. 호출부 호환성을 위해
입력 계약이 달라지는 후속 구현은 `POST /backtests/runs`과
`GET /backtests/runs/{run_id}`를 검토한다. 저장과 실행은 후속 범위다.

| 입력 | 계약 |
|---|---|
| 전략 | 서버 허용 목록의 `strategy_id` 및 불변 버전. 승인된 전략만 선택 |
| 종목·레버리지 | 서버에서 BTCUSDT와 1배 고정. 명시된 다른 값은 422 |
| 기간·자금 | 오프셋이 있는 `start`, `end`, 양수 `initial_equity_usdt`. 기간 상한과 워밍업 요구량을 검증 |
| 수수료·슬리피지 | 비음수 bps. 진입·청산에 각각 적용하며 계산에 쓴 값을 결과에 저장 |
| 펀딩 | `historical` 또는 명시적인 `disabled`. 실제 모드는 정산 시각별 요율, 보유 방향, 포지션 명목액으로 반영. 요율 누락 시 실패 |

접수 후 `202`와 실행 ID를 반환한다. 장기간의 분봉 재생은 전용 백그라운드 워커에서
실행한다. 기존 실행 이력과 사용자·전체 동시 실행 제한의 재사용 여부를 검토한다.
작업 상태는 `queued`, `running`, `succeeded`, `failed`로 조회한다.
재시작 뒤에도 작업을 추적할 수 있도록 상태를 보존하고 결과·내역은 요청자에게만 노출한다.

완료 응답은 비용 반영 순수익률, 평가자산 고점 대비 최대 낙폭(MDD), 순이익 거래 합계를
순손실 거래 합계의 절댓값으로 나눈 PF, 청산된 거래 수, 시간순 거래 목록 및 평가자산 곡선을
포함한다. 손실 거래가 없어 PF 분모가 0이면 `null`을 반환한다. 거래 내역에는 진입·청산
시각/가격, 방향, 수량, 비용 및 순손익을 넣고 거래와 자산 곡선은 페이지 단위로 조회한다.

실행이 시작되면 당시 닫힌 봉의 시간 상한과 원본 스냅샷을 확정한다. OHLCV와 펀딩 데이터의
버전 또는 체크섬, 실행기 및 전략 버전, 입력값을 함께 기록한다. 워밍업 기간까지 필요한
1분봉이 빠짐없이 존재하는지 검사하고 누락·중복이 있으면 실행을 중단한다. 집계 봉은
`봉 시작 + 간격`에 공개되며 의사 결정 시각까지 닫힌 봉만 신호에 사용한다. 시가 체결
모형은 신호를 계산한 뒤 체결할 수 있는 다음 봉의 시가를 사용한다. 예를 들어 09:00~10:00
봉의 종가는 10:00부터 사용 가능하고 09:00 시가 체결에는 사용할 수 없다. 동일 분봉에서 손절과
익절이 모두 닿는 경우의 처리 순서는 전략 테스트 전에 계약으로 정해 결과에 기록한다.

## 검증 실행

앱 설정은 일반 테스트용 환경변수로 구성한다. `pytest`와 `httpx`가 필요하다.
별도의 PostgreSQL 테스트 DB를 `BACKTEST_TEST_DATABASE_URL`로 지정하면
임시 테이블에 데이터를 만들고 읽기 전용 트랜잭션에서 API를 검증한다.

```sh
python -m pytest -q tests/test_backtest_data.py
```
